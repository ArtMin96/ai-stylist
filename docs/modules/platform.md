# Module Contract — `platform`

> Module names are canonical per [SPINE §3](../../planning/SPINE.md). Path: `apps/api/src/platform`. This contract is the module's source of truth; code that contradicts it is wrong until a DEC entry says otherwise.

- **Responsibility (one sentence):** Infrastructure adapters that implement the ports declared by domain modules: storage (R2), durable jobs (pg-boss), outbox relay, logger, OTel init, PostHog server, resilience utilities, provider SDK wrappers; deployment target is owned servers + Coolify (DEC-42).

## Invariants

1. Adapters translate only: no business rule lives in any adapter, task body, or provider wrapper (doc 04 §4.2 rule 9).
2. This module writes only the tables it owns (doc 04 §4.2 rule 8); cross-module behaviour goes through public application services or events.
3. Presigned URLs are short-lived (doc 11 §5.4): GET (read) TTL is clamped to ≤ 10 minutes (`MAX_PRESIGN_GET_TTL_SECONDS`), PUT/multipart (write) TTL to ≤ 15 minutes (`MAX_PRESIGN_PUT_TTL_SECONDS`), and a TTL under 1 second is refused; `expiresAt` is never later than the URL's real expiry. Asserted in `apps/api/src/platform/tests/storage.port.test.ts` and, for R2 URLs (`X-Amz-Expires`, an expired PUT and GET refused by a SigV4-verifying endpoint), `r2-storage.sec.test.ts`.
4. The outbox relay claims at most 100 rows per poll (`MAX_OUTBOX_BATCH_SIZE`; a larger `batchSize` is rejected), and concurrent relays never claim the same row (`FOR UPDATE SKIP LOCKED`). Proven by `outbox-relay.test.ts` ("rejects a batch above 100 …"), `outbox-relay.docker.test.ts` ("two relays on one table … never > 100 per poll") and AC-5 in `apps/api/src/jobs/tests/acceptance-dispatch.docker.test.ts`.
5. No payload or foreign error text is stored or logged: `last_error` holds the error class plus `(pg <SQLSTATE>)` (the message only for the relay's own errors), a failed job's pg-boss `output` is `{ errorName, pgCode? }`, and logs carry ids, queue, attempt and error class only. Proven by `outbox-relay.test.ts` (`describeSendError`), `outbox-relay.docker.test.ts` ("never stores or logs a send error message that echoes the payload …"), `queue.docker.test.ts` ("fails a job after exactly retryLimit retries and dead-letters it": stored output has no payload marker) and AC-2 in `acceptance-dispatch.docker.test.ts`.
6. One job per idempotency key: the job id is the UUIDv5 of the key (the outbox event id), so a repeated `send()` or relay re-dispatch inserts nothing. Proven by `queue.docker.test.ts` ("enqueues exactly one job when the same idempotency key is sent twice"), `outbox-relay.docker.test.ts` ("… exactly one job keyed by the event id, also on re-dispatch") and AC-1.
7. A guarded side effect runs at most once per key for its retention, durably: `PgIdempotencyGuard` records the key only with a completed effect, and a thrown effect leaves no key. Proven by `idempotency.docker.test.ts` and AC-3 (replay after pg-boss dropped the job makes no second worker call).
8. No pg-boss DDL runs on boot: pg-boss starts with `migrate: false` and `start()` refuses an unmigrated database; migration 0003 must equal the installed pg-boss's construction plan. Proven by `queue.docker.test.ts` ("refuses to start before `just db-migrate` installed the pg-boss schema") and `apps/api/tests/migrations/pgboss-schema.test.ts`.
9. A dead-lettered job marks its outbox row `failed` (idempotently, first reason kept), and the relay never re-dispatches a `failed` row. Proven by `outbox-dead-letter.docker.test.ts` and AC-2 in `acceptance-dispatch.docker.test.ts`.
10. After `cancelUser(userId)` resolves, no job keyed to that user reaches a handler on any instance for 100 days (`CANCELLED_USER_MARKER_RETENTION_SECONDS`: 90-day outbox replay + 7-day deletion grace + margin): `send` refuses the user and `work` cancels a racing job without calling the handler. Proven by `queue.docker.test.ts` ("keeps a cancelled-user marker 100 days …"), AC-6/AC-7 in `acceptance-lifecycle.docker.test.ts` and `apps/api/src/jobs/tests/batch-settlement.docker.test.ts`.
11. Spans and logs carry ids and enums only (doc 14 §3, doc 11 §8). The platform's own spans (`outbox.dispatch <event type>`, `job.process <queue>`) set ids, enums and `correlation_id` only and record a failure by error class; `SanitizingSpanExporter` strips every exported span of query strings (`url.query`, the query of `url.full` / `url.path`), client IPs, user agents, status messages and exception messages and stack traces, writes an `exception.type` that is neither name-shaped (`errorNameShape`) nor code-shaped (`codeShape`, both `LOG_REDACTION_RULES` of `packages/shared-kernel`, registry `log-redaction.json`, the one source the workers read too) as `Error` (OTel JS fills it from `String(err.code)`, else `err.name`, and either can be free text), and redacts attributes named with a forbidden log word. That attribute rule (`sanitizeAttributes`) covers the attributes of the span, of every event and of every link (the linked trace id, span id and flags are kept), and the span name and every event name are cut at the first `?` or `#`; `GET`, `outbox.dispatch <event type>` and `job.process <queue>` come out unchanged. OTel log records are the pino lines after the logger's redaction. Not covered: the value under a key that is neither dropped, forbidden nor a URL attribute is not inspected. Proven by `trace-context.test.ts` (with "keeps exception.type only when it is name- or code-shaped …", the `LOG_REDACTION_EXAMPLES.exceptionType` vectors through `sanitizeAttributes` ("span sanitizer: exception.type vectors …"), "cuts the query and fragment from a span name …", "… from an event name …" and "sanitises link attributes …"), `telemetry.process.test.ts` ("… ids only") and `logger.redaction.test.ts` (behind the telemetry entry, no planted value on stdout or in any OTLP body).
12. Without `OTEL_EXPORTER_OTLP_ENDPOINT` the telemetry entries start nothing: no loader hook, no SDK, no exporter, no network; logs still carry `correlation_id`. Proven by `telemetry.process.test.ts` ("without an OTLP endpoint nothing starts …").
13. One trace and one correlation id cover API request → outbox → job → worker call (doc 14 §2–§3): `PgOutboxWriter` stores the active span's `traceparent` in an envelope without one, the relay's PRODUCER span and the job's CONSUMER span are parented on it, the job runs in the envelope's correlation scope, and the worker request carries the job's `traceparent` (undici) and `x-correlation-id`. An inbound `x-correlation-id` is accepted only as 1–128 chars of `[A-Za-z0-9._:-]`, else minted. Proven by `apps/api/src/jobs/tests/trace-propagation.docker.test.ts` (P02-T09 AC-1) and `correlation.test.ts`.
14. Metrics (planning/14 §4) carry route templates, queue names and enums only: never an id, a raw path or user-derived value. The names are fixed and every `stylist_api_*` / `stylist_queue_*` series and label the Grafana dashboards and alerts query is emitted; `stylist.api.request.duration` is in seconds with explicit buckets; every counter series of a known route or job type starts at 0 when the process starts, so the first dead letter after a restart fires `queue.job.dlq`. Proven by `request-metrics.test.ts`, `queue-metrics.test.ts`, `metrics-catalog.test.ts` and `apps/api/src/jobs/tests/queue-metrics.docker.test.ts` (an injected failure through retry → DLQ moves `stylist.queue.job.dlq` from 0 to 1).
15. Feature flags never capture: `PostHogFeatureFlags` sends only `POST <host>/flags/` (one bounded request per 10 s for the fixed system distinct id, no person properties, GeoIP off) and refuses every other request before the network. A flag absent from a clean reply (inactive in PostHog) is off; a timeout, error or quota-limited reply answers the registry's `defaultWhenUnavailable`; `isEnabled` never throws. Proven by `feature-flags.test.ts`.
16. A logged error is an allowlist (doc 11 §8): the `err` serializer, and the logger's walk over an Error under any other key, write `{ type, code?, cause? }` only, for an Error of any realm (`isError` in `errors/error-shape.ts`: `Error.isError` where the runtime has it, never a bare `instanceof Error`, which misses an Error made in a `vm` context and would let the walk copy its enumerable fields; on a runtime without `Error.isError`, such as Node 22, it falls back to `instanceof Error` instead of throwing): the error class (an `Error.name` that does not match `errorNameShape` is written as `Error`), a code-shaped `code` (`codeShape`: Postgres SQLSTATE or Node system code) and the same for at most `maxCauseDepth` (5) `cause` links; the shapes and the depth are `LOG_REDACTION_RULES` of `packages/shared-kernel` (registry `log-redaction.json`), applied by `errors/error-shape.ts` and `logger.ts`, never a local copy; a non-Error throw is its `typeof`. Never the message, the stack or a driver field (`detail`, `where`, `hint`, the query or its parameters). `msg` is only the string the caller wrote (`hooks.logMethod`): an error logged without a message gets `error logged` where pino would copy `err.message`, an Error first argument of any realm is logged as `{ err }`, and a first argument that is neither a string nor an object (`logger.info(31415926)`), printf-style arguments and a non-string message are dropped. The `context` field nestjs-pino writes from a Nest `Logger` call's last optional argument is kept only when it is a PascalCase class name (`nestContextShape` of `LOG_REDACTION_RULES`, such as `ProblemFilter` or `RoutesResolver`); anything else, such as the stack of `error(message, err.stack)`, the value of `warn(message, value)`, an access key id (`AKIAIOSFODNN7EXAMPLE`), a `tok_…` token or a dotted name, is written as `[REDACTED]`. Every first-party and Nest-internal context is a class name (`ProblemFilter.name`, `NestFactory`, `InstanceLoader`, …). Child loggers are made with `childLogger(parent, bindings)`, which applies the same rules to the bindings: pino writes raw `.child()` bindings without the log formatter, so only the exact-word redact paths would reach them. Code logs an error under `err`, never a name it computed itself. `ProblemFilter` logs a 5xx as `unhandled error` (context `ProblemFilter`) with that `err`. Proven by `logger.redaction.test.ts` ("keeps err to the error class and SQLSTATE …", "summarises the cause chain …", "logs a thrown non-Error by its type only …", "logs an error name that is not identifier-shaped as Error …", "summarises an Error under any other key …", "redacts child-logger bindings like a logged object …", "never writes error text or interpolation arguments into msg", "drops a first argument that is neither a string nor an object", "summarises a cross-realm Error like any Error …", "through the API error path …", including a Nest `Logger.error(error)` without a message and "keeps a Nest Logger context only when it is a name …" with `new Logger()` and static `Logger` calls from `@nestjs/common`, and the `LOG_REDACTION_EXAMPLES.nestContext` vectors through `pinoLogFormatter`), `error-shape.test.ts` (including "falls back to instanceof Error when Error.isError is missing") and `feature-flags.test.ts` ("logs a failed client shutdown through the err allowlist …").
17. A URL that platform logs or records is cut at the first `?` or `#` by one function, `stripQuery` in `logger.ts` (not re-exported): the logged `req.url`; the problem `instance`, and the request URL wherever the problem `detail` quotes it (Nest's unknown-route 404, `Cannot GET <url>`) (`ProblemFilter`); the `instance` of the problem body `frameworkErrors` sends for a request Fastify answers before routing (a malformed path such as `/v1/x%zz`, `FST_ERR_BAD_URL`; a too-long path parameter; a failing async constraint), which carries no `detail` because Fastify's message quotes the raw URL; the span name and every event name; and the attributes `url.full`, `url.path`, `http.url` and `http.target` wherever `sanitizeAttributes` applies (span, event, link, resource). Such an attribute is cut whatever its shape: the string, or each string of an array value (cut rather than dropped, so the path stays searchable). A query string or a fragment can carry a signed-URL credential, a token or user input, so a new place that writes a URL calls `stripQuery` instead of cutting the string itself. Proven by `logger.redaction.test.ts` ("cuts a logged url at the first ? or # …", "through the API error path …", whose request carries a query and whose problem `instance` is the path, "answers a malformed URL with a problem body …" and "answers an unknown route with its path only …") and `trace-context.test.ts` ("strips query strings, network identity and free text …", "cuts every string of an array-valued URL attribute", "cuts the query and fragment from a span name …", "… from an event name …").
18. The process resource is sanitized once, where it is built, never per signal: NodeSDK gives one resource to the trace, metric and log providers, and only spans pass `SanitizingSpanExporter`. `startTelemetry` runs the env detector itself (`OTEL_SERVICE_NAME`, `OTEL_RESOURCE_ATTRIBUTES`; no host or process detector), applies `sanitizeAttributes` to the merged attributes and starts NodeSDK with `autoDetectResources: false`, so no environment value reaches a span, a metric or a log record unsanitized. `service.name`, `service.version`, `deployment.environment.name` (the attributes the dashboards and alerts filter on, as `service_name`, `job` and `deployment_environment_name`) and other attributes without a forbidden word in their last dot-segment pass unchanged; a forbidden one is exported as `[REDACTED]`. Adding a resource detector means adding it inside that step, not to NodeSDK. Proven by `telemetry.process.test.ts` ("sanitises the resource all three signals share …": a value planted in `OTEL_RESOURCE_ATTRIBUTES` is in no OTLP body, the legitimate attributes are in all three) and `trace-context.test.ts` ("sanitises the process resource …").
19. Every object key is `u/<userId>/<namespace>/<key>` (doc 11 §4.3, so account deletion lists one prefix per user, §13.2 step 4), and a presigned URL addresses only `<key>` inside its own user's namespace (`uploads`, `derived`, `avatars`): a `userId` that is not a `usr_<ULID>` (`isId`, shared kernel), an unknown namespace and a key that is absolute or has an empty, `.` or `..` segment or any character outside `[A-Za-z0-9._-]` and `/` are refused before signing, by both adapters, so no request reaches outside `u/<its userId>/` (a key spelling `u/<other user>/…` is a nested path inside the caller's own namespace). The R2 path is signed, so a URL edited to another user, namespace, key or bucket is refused. Which user a request may act for is the calling module's authorization (it passes the authenticated principal's id), not this adapter's. Proven by `r2-storage.sec.test.ts` ("per-user key layout …": a PUT and a GET URL of user A edited to user B's prefix, two users at the same namespace and key, a key spelling another user's prefix; "refuses a malformed user id …", "refuses keys that could leave the namespace …", "refuses a foreign namespace", "rejects a URL edited to another namespace, key, bucket or a longer expiry"), `storage.port.test.ts` ("stores every object under u/<user id>/ …") and, against R2, `r2-storage.live.sec.test.ts`.
20. A presigned PUT signs `content-type` (a bare `type/subtype`) and `content-length` (= `sizeLimitBytes`): an upload of another type or of another size, larger or smaller, is refused by the endpoint's signature check. Proven offline by `r2-storage.sec.test.ts` ("rejects an upload of another content type", "rejects a body larger or smaller than the signed size") and against R2 by `r2-storage.live.sec.test.ts`. The content-type allowlist and maximum upload size of doc 11 §5.4/§5.5 are the `media` caller's rules, enforced before it asks for a URL (a P06 exit criterion), not this adapter's (invariant 1). `Content-Encoding` is not signed and R2's handling of an unsigned one on a presigned PUT is unverified, so P06 workers fetch originals with HTTP decompression disabled.
21. The storage adapters never log or put into an error message a presigned URL, its query (signature, access key id), the user id, the object key, the content type or a credential; the R2 adapter logs `method`, `namespace`, `ttlSeconds` and a `refusal` enum only, and holds its credentials in `#private` fields, so `util.inspect` and `JSON.stringify` of the provider show neither the access key id nor the secret. Proven by `r2-storage.sec.test.ts` ("… never the URL, its query, the key, the type or a credential", "logs the refusal reason, never the rejected value", "keeps the credentials out of util.inspect, JSON.stringify and own properties") and `storage-provider.test.ts`.
22. The in-memory storage provider is never bound outside local, dev and test runs: with none of the four `R2_*` keys, `loadConfig` refuses to boot when `APP_ENV` is `staging` or `prod` or `NODE_ENV` is `production` (`isLocalOrDevDeployment` in `apps/api/src/config.ts`, fail closed, the one predicate the dev routes use too; doc 15 §11), with a `ConfigError` that names the keys and the rule, never a value. Behind it, `createStorageProvider` requires `allowsInMemory` (no default) and refuses the in-memory provider when the composition root passes `isLocalOrDevDeployment(config)` as `false` (the predicate stays in `config.ts`, which platform may not import). `config.ts` checks the `R2_*` keys for presence and all-or-none only; the shape of each is checked once, by the R2 adapter, which `AppModule.forRoot` builds at boot, so a malformed key fails `createApp` with a `TypeError` naming the key (`R2: bucket (R2_BUCKET) must be …`), never the value. Proven by `apps/api/tests/config.test.ts` ("refuses to boot without R2 keys when …", "keeps the in-memory provider for local, dev and test runs", "a malformed … loads but fails boot, naming the key and never the value") and `storage-provider.test.ts` ("refuses the in-memory provider when the environment does not allow it", "refuses a malformed key by name, never echoing its value").
23. A problem `detail` never carries a foreign message: a 4xx answers with `detail` only from an `HttpException` (code that wants a detail throws one; the rate-limit builder does) or from a known Fastify request error (`FST_ERR_CTP_INVALID_JSON_BODY`, `FST_ERR_CTP_EMPTY_JSON_BODY`, `FST_ERR_CTP_INVALID_MEDIA_TYPE`, `FST_ERR_CTP_BODY_TOO_LARGE`, `FST_ERR_CTP_INVALID_CONTENT_LENGTH`), whose detail is the filter's own fixed text for that code, never the thrown value's message. Any other thrown value with a 4xx `status` or `statusCode` (a provider SDK's HTTP error, whose message can quote a presigned URL and its signature) answers without `detail`; a 5xx never carries one (except a 503 from an `HttpException`). A request body in a media type the route does not accept is `UNSUPPORTED_MEDIA_TYPE` (415). Proven by `problem.test.ts` ("never echoes the message of a non-HttpException 4xx …", "keeps the fixed detail of a known Fastify request error, never its message", "maps 415 … to UNSUPPORTED_MEDIA_TYPE") and `apps/api/tests/http.test.ts` ("a malformed JSON body answers a 400 problem with a fixed detail", "a body in an unsupported media type answers a 415 …", the 429 detail).

- `apps/api/src/modules/**` entirely — public API included (`platform-leaf`); `apps/api/src/jobs/**` too (queue names and routing are injected by the composition root).
- (Provider SDKs are allowed here — this is the only place they may be imported, besides the `jobs/` composition root; `domain-no-provider-sdk` bans `pg-boss` in modules.)

- Logger: allowlist serialization + forbidden-key denylist (doc 11 §8); `console.*` and raw `req.body` logging are lint errors (P02 §6). The denylist words have one name, `FORBIDDEN_LOG_KEYS` in `packages/shared-kernel`: import it from there, platform does not re-export it.
